# 未读文章 → Kindle epub（免确认直推）

## 前置检查（每次运行第一步）

1. 确认命令行可用：`x6o4 status`（npm 全局安装：`npm install -g x6o4-tools`；未安装时也可 `node <仓库路径>/cli/x6o4.js status`）。
2. 若报「配置未就绪」或令牌无效：引导用户在**终端亲自**运行 `x6o4 login`（交互式长命令，用户亲自输入邮箱密码，你不要代输、不要索要密码）；登录成功后再继续。
3. 若 status 显示权益无效（SUBSCRIPTION_*）：如实告诉用户需要续订或领取试用后才能读取文章，终止本次。

## 执行流程（全程无需向用户逐项确认）

调用即授权：用户让你推 Kindle，就是发送与标记已读的授权。正文永不读入对话，只依据元数据与摘要判断。

1. **读推送参数**：
   ```
   x6o4 config show
   ```
   记住两个数：凑篇目标 N 篇/次（`unread.max_articles_per_run`，默认 30）与邮件附件体积上限 MB（`mail.max_attachment_mb`，默认 45，第 4 步要用）。
2. **循环凑篇**（元数据 + 160 字摘要进对话，全文留在本地文件；批号从 1 递增）：
   ```
   x6o4 entries --status unread --sync --fill 50 --print --out /tmp/x6o4-unread-1.json
   ```
   （`--sync` 增量拉取：只取编号比本机游标大的文章、按到达顺序从旧到新，与阅读 App 的增量同步同一机制，已取过的文章永不重复取；每批 `--out` 写入成功后游标自动推进到本批窗口尾，下一批自动续接。`--fill 50`：逐页翻取直到凑够 50 条可推候选或取尽——大量短文占住最前面时不会卡死。Windows 用 `%TEMP%` 等临时目录；下同。用户说过「只推某分类/某源」时，先 `x6o4 feeds` 查编号再加 `--category-id N` 或 `--feed-id N`（行首数字是订阅源编号，分类方括号 `[#12 kindle]` 里的 12 是分类编号）：筛选拉取只推进该筛选自己的游标、全局游标不动，且第 5 步的游标回拨也要带同样筛选参数。）
   对每批候选**从旧到新逐条评估**，够格的记入入选清单，**凑满 N 篇即停止评估**（本批更后面的不再看）。评估标准（语义细筛）：依据标题、来源、时长、摘要剔除不适合 Kindle 长阅读的——公告/通知、视频集合、纯图集、快讯短讯、招聘/广告帖；用户在对话里给过偏好的按偏好来。
   结束循环的条件（任一满足）：入选 ≥ N / 输出顶层 `exhausted: true`（未读池已取尽，再拉也没有）/ 已拉 3 批（150 条候选保险丝——防内容质量差的日子把整个未读池的摘要灌进对话；触发后有多少发多少）。
3. **定量**：入选超出 N 时取最旧的 N 篇；生成与阅读顺序同为从旧到新。筛完 0 篇则不发不标，直接汇报「没有适合的内容」。
4. **生成 epub**（`--from` 逗号分隔全部批次文件；`--ids` 按从旧到新传全部入选；`--max-mail-mb` 用第 1 步读到的值。不传 `--out` 与 `--title`：文件名与书内书名自动统一为「RSS 阅读-当天日期-文章标题」，同一批文章重复生成同名覆盖；从输出取实际文件名）：
   ```
   x6o4 build-epub --ids 9001,9002,... --from /tmp/x6o4-unread-1.json,/tmp/x6o4-unread-2.json --max-mail-mb 45
   ```
   输出逐册一行（篇数 / 图 / 大小 / 条目编号）；总体积触顶时额外输出「因体积未入选 X 篇」清单——这些条目**保持未读**；末行「最后入选条目 id」第 5 步要用。输出中的「全文拉取」行统计摘要源处理情况（配置/启发式/失败保留原文），防盗链图片自动分级下载，无需任何参数。
5. **回拨游标**（生成成功后立即执行、在发送之前；用上一步的「最后入选条目 id」）：
   ```
   x6o4 sync set 11847
   ```
   （分类/源筛选运行改为 `x6o4 sync set <id> --category-id N`（或 `--feed-id N`）。作用：没进书（配额外、体积外、没轮到评估）的条目全部落在游标之后，下次运行自动再取、再有机会推送；已进书的已随游标越过且第 8 步会标已读，不会重复。）
6. **持久化发现的摘要源**（「全文拉取」行三项计数全 0 时显示「无需拉取」，跳过本步；仅当行尾列出「可保存拉取原文设置的源」时，逐个编号执行）：
   ```
   x6o4 feeds config --id <源编号> --full true --referer false
   ```
   把「拉取原文」保存到服务端（App 与网页管理页共用同一份设置，后续运行不再依赖启发式）；失败不阻断本次推送。
7. **发送**（自动，一封邮件带全部分册；文件用第 4 步输出的实际路径，邮件主题也默认取文件名）：
   ```
   x6o4 send-kindle --file <实际文件1>[,第2册,...]
   ```
8. **标记已读**（仅实际进入 epub 的条目 = 各册行「条目 …」里编号的汇总，**不含**「未入选」清单；发送受理后执行）：
   ```
   x6o4 mark-read --ids 9001,9002,...
   ```

## 事后汇报（唯一的用户交互）

一次性汇报：已推送 N 篇（清单：标题 + 来源 + 阅读时长）、筛掉 K 篇（各附一句理由）、未入选 X 篇（体积上限挤出，保持未读、下次自动再取：清单）、已标记已读 M 篇、全文拉取统计（配置 X / 启发式 Y / 失败保留原文 Z，及已持久化的源）、失败明细（如有）。
用户说「把某篇/没推的也推给我」时：那些文章的全文就在批次 JSON 文件里 → 用其 id 重复生成（`--max-mail-mb` 同值）、发送、标记，然后把游标摆到补推的最末一篇（`x6o4 sync set <id>`，仅当它比当前游标新）。
用户明确说「从头重新筛一遍」时：先 `x6o4 sync reset` 清零游标再走流程。
位于最后入选篇**之后**的被筛条目下次还会出现、再判断一遍（属预期：有选中篇越过它们即翻篇）；同一批低质条目反复出现时可用 `x6o4 skip add --ids ...` 压制（30 天）。

## 失败处理

- 任何命令失败：完整呈现错误原文（错误信息已含中文指引），不要静默吞掉、不要盲目重试。
- 发送失败（授权码失效/未加白名单）：游标已在第 5 步回拨，已入选内容不受影响——epub 在本地，按下面指引重试或兜底，成功后补跑第 8 步 mark-read。提示两个前提——SMTP 发件地址需加入亚马逊「认可的发件人」列表；亚马逊中国区个人文档服务已停运，需国际区 @kindle.com 邮箱。可数据线拷贝或 Send to Kindle 网页版上传（200MB）兜底。
- 配置 `mail_transport` 为 `agently` 时（用 agent mail 产品的 agently-cli 发信，无授权码；agent mail 是腾讯的独立邮箱产品，不是 QQ 邮箱）：报「未找到 agently-cli 命令」提示先 `npm install -g @tencent-qqmail/agently-cli`；报未登录则引导用户在终端亲自运行 `agently-cli auth login`（浏览器授权，用户亲自完成，不要代操作）。
- 令牌 401：引导重新 `x6o4 login`。

## 铁律

- 正文与令牌/授权码不进对话；status 只显令牌前缀。
- 只标记实际进入 epub 的条目；被筛掉与未入选的保持未读。
- 只通过 `x6o4` 命令行完成流程；命令行没提供的信息先用命令行查（如 `x6o4 feeds`、`x6o4 config show`），查不到就如实告诉用户缺什么，不直接调用包内部模块或接口。
- 不新增任何事前确认环节（用户的话就是授权）；只有指令未覆盖的破坏性动作（清空收藏、吊销令牌等）才需要确认。
